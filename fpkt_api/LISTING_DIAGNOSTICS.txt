Flipkart API listing diagnostics

실행 경로
- schedule/fpkt_api_run_all.bat -> fpkt_api/ops_test.py가 API 운영 수집 경로입니다.
- ops_test.py라는 기존 이름을 유지했습니다. BAT 기본 모드는 DB insert입니다.
- 기존 Playwright 진단 함수와 설치 점검은 유지합니다.

목표 수량까지 수집 (2026-10-06 변경)
1. MAIN/BSR 매 페이지의 API 상품 배열 개수, 기존 파서 추출 개수, 상품 ID,
   페이지 내 고유 수, 이전 페이지와 중복 수, 서버 표시 범위/총수/총페이지를 기록합니다.
   원본 배열 개수는 위젯별로도 남겨 새 위젯과 기존 파서 차이를 확인합니다.
2. 10개 페이지도 수집합니다. MAIN/BSR 각각 상품 ID로 중복을 제거하고 먼저 나온
   순서를 유지하며 고유 MAIN 300개, BSR 100개까지 진행합니다. 마지막 페이지에서
   목표를 초과하는 상품은 최종 결과에 추가하지 않습니다.
3. 원래 요청/응답 요약을 매 페이지 저장합니다. 상품명, 페이지 내 위치, 실제
   누적 노출 순서도 기록합니다. source_rank는 24개 고정 계산 대신 실제 수신 순서,
   main_rank/bsr_rank는 중복 제거 후 1부터 시작하는 순위입니다.
4. 10개라는 이유로 API 비교 요청이나 브라우저 캡처를 자동 실행하지 않습니다.
   따라서 10개 페이지가 반복돼도 진단 재요청 때문에 수집이 지연되지 않습니다.
5. MAIN/BSR 전체에서 10개 페이지와 24개 페이지가 모두 발견되면 해당 품목의
   상세/리뷰까지 수집하여 파일로 보관하되 DB 적재는 전체 보류합니다.
   MAIN 10개/BSR 24개처럼 단계 간 차이도 혼합입니다. 마지막 페이지를 목표 수에
   맞춰 일부만 채택한 경우에는 채택한 수가 아니라 원본 응답 수로 판단합니다.
   --allow-qa-insert로도 보류를 우회할 수 없습니다. 혼합 건은 로컬 로그만 남기고
   메일을 발송하지 않습니다. 다른 품목은 각자의 결과로 판단합니다.
6. 혼합 보류는 수집 후 종료 코드 86을 반환합니다. 기존 BAT는 86을 자동 재수집하지
   않으므로, 재시도에서 혼합 증거가 사라지고 DB에 들어가는 일을 방지합니다.
7. 기존 --max-pages-main/bsr 값은 안전 상한으로 사용하되, 최소한 해당 목표 수만큼의
   페이지를 허용합니다. 기본 목표에서는 MAIN max(기존값, 300), BSR max(기존값, 100).
   기존 30/15 설정이 남아 있어도 목표를 채울 때까지 넘어갈 수 있습니다.
   서버의 hasMorePages=false, 연속 3페이지 신규 상품 없음, 안전 상한 도달 시에는
   부족 수량과 원인을 listing_errors.csv에 남기고 DB 적재 없이 86으로 종료합니다.
   네트워크 오류의 기존 재시도 정책은 유지합니다.

자료 위치
fpkt_api/test_output/ops_<품목>_<실행시각>/
  summary.txt                             전체 결과와 진단 경로
  listing_pages.csv / listing_errors.csv   페이지별 결과와 중단 이유
  main_raw.csv / main_final.csv            MAIN 원본 처리 행 / 중복 제거 결과
  bsr_raw.csv / bsr_final.csv
  diagnostics/listing_observations.jsonl   매 페이지 안전한 요청/응답 요약
  diagnostics/<단계>_baseline_24.json      같은 실행·단계의 최근 정상 24개
  diagnostics/mixed_page_sizes.json       혼합 발생 페이지, DB 보류 이유 (혼합 시)

이전 중단 방식에서 생성한 자료 (새 수집에서는 자동 생성하지 않음)
  diagnostics/<단계>_page<N>_ten_products/
    summary.txt                           사람이 읽는 요약
    report.json                           원래 응답, 비교 실험, 브라우저 관찰
    browser.png                           실제 브라우저 화면 1장 (성공 시)
    browser_initial.html                  최초 화면 텍스트만 HTML로 보관
    browser_after_scroll.html             스크롤 후 화면 텍스트

주의할 해석
- server_returned_ten_products: 원본 상품 배열 자체가 10개입니다.
- parser_count_mismatch: 원본 배열과 추출 개수가 다릅니다. 위젯별 수를 함께 확인합니다.
- last_page_ten_products: 서버가 마지막 페이지라고 표시한 정상 잔여 10개일 수 있습니다.
  새 방식에서는 개수만으로 중단하지 않고 목표 수와 서버의 종료 신호를 확인합니다.
- DOM 수는 Add to Compare가 있는 상품 링크의 고유 PID를 우선 사용합니다.
  없는 레이아웃은 보이는 상품 링크의 고유 PID를 사용하며 heuristic으로 명시합니다.
- API와 브라우저는 동일 세션이 아닙니다. 서버 실험/세션 정책 원인을 단정하지 않습니다.
- 쿠키, 인증 헤더, 세션 본문, HAR 원본, 브라우저 프로필은 진단 파일에 저장하지 않습니다.
  요청 URL의 검색 필드와 허용된 클라이언트 헤더/숫자 페이지 제어값만 남깁니다.

캡처 설치와 점검 (수집 실행 없음)
RDP에서 스케줄러와 같은 Windows 계정/Python 환경, 저장소 루트에서 실행합니다.
CMD:       call schedule\fpkt_api_setup_capture.bat
PowerShell: .\schedule\fpkt_api_setup_capture.bat
Git Bash:  python fpkt_api/check_capture.py --install

이 설치 BAT는 고정 버전 Playwright와 Chromium을 필요한 경우 설치한 뒤
외부 요청을 차단한 로컬 HTML로 PNG 생성만 점검합니다. DB/메일/수집은 실행하지 않습니다.
설치 후 점검만: python fpkt_api/check_capture.py
테스트 PNG 보관: python fpkt_api/check_capture.py --out fpkt_api/test_output/capture_check.png
패키지/브라우저 설치는 공식 Playwright Python 방식입니다:
https://playwright.dev/python/docs/browsers

운영 BAT도 git pull 이후 같은 설치·점검을 수행합니다. 실패하면 수집을 시작하지 않고
ops_all_<시각>/capture_setup.txt에 기록합니다. 준비된 환경에서는 다시 다운로드하지 않습니다.
